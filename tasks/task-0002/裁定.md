## 裁定1｜0029 模式同构：就地实现（选项A），不抽象共用层

**必裁信号**：第二实例——`DocumentNode` 判别联合封闭与 `DocumentConfigContext.tsx:64-69` 的 `Action` 联合构成逻辑同构（同属「判别联合＋全量 switch 消费」模式），勘探员按规则上报双选项。

**候选与论据**：
- A（选定）就地实现：各类型文件内定义联合；`assertNever` 辅助放 `types/ast.ts` 供四消费点 import。
- B（否决）抽象共用层（建 types/discriminated.ts 通用层）：联合定义是类型声明、无运行时载体，两个实例间**不存在可共用代码**——唯一候选实体是 3 行 `assertNever` 函数，为此建一层目录/文件是负收益。

**「为何不会有第三实例」的正面回答（选就地的法定义务）**：判别联合是 TypeScript 语言特性级模式，每个实例的判别键、成员集、payload 形状完全不同（Action＝5 成员 reducer 动作；DocumentNode＝13 成员数据节点），彼此无可归并的领域。若第三实例出现，它要共用的至多是 `assertNever`——该函数已放在 `types/ast.ts` 可直接 import，届时再评估提升为独立共享模块即可（一处函数搬家，零迁移成本）。抽象时机未到，预设层是猜未来。

**方案三问**：
- 行为保持还是改变？**行为保持**——纯类型层＋测试网扩展，运行时零变化（红线：AST 结构与 sentenceId 生成不动）。
- 如何验证？npm test 全量 331 用例绿＋npm run build（tsc -b）绿＋抽验「临时加假枚举成员应在 4 处 switch 报错」＋git diff 不含运行时逻辑变更。
- 如何回滚？git revert 单提交回滚；无可逆面（无数据迁移/部署/外部调用）。
