## 二、0005 候选方案对比

| 维度 | 方案 A-简（推荐） | 方案 A-行 | 方案 B（计算式测量） |
|---|---|---|---|
| 内容 | measurer 渲染真表格＋usePagination 纳入 table 元素、整表格＝单个 line（不可分割） | 同 A-简但按 `<tr>` 粒度拆 line（断点可落表格行间） | 决策层参数→JS 公式算高（行高×行数＋padding＋border，需估列宽折行） |
| 精度 | 与渲染同 DOM，最高（cell 文本折行自动正确） | 同 A-简 | 与 CSS 实际渲染有系统性偏差（字体 fallback、table-layout auto 列宽算法） |
| 对断点计算牵连 | `:scope > p` → `:scope > p, :scope > table`；table 走单行分支（:181-183 同构形状）；Phase 1/2 **零改动**（表格 line 进 lines 数组后自动参与） | 行收集需逐 tr 度量（tr.offsetTop/offsetHeight），断点逻辑同 | 行收集不变，但高度来源换公式——分页断点全依赖公式精度 |
| 对版头避让牵连 | 无（firstPageAvailable 机制不区分行来源） | 无 | 无 |
| 对版记避让牵连 | 无（Phase 2 以 lines 为输入，表格 line 自动参与；表格整体推页行为与现状单行段落超高一致） | 表格行逐行参与，语义更细 | 同 A-简 |
| 已知限制 | 巨型表格（高于一页可用高）推到新页起后仍超高→viewport overflow hidden 截断底部（与现状单行段落超高行为一致，保持） | 截断处表格边框丢失（table 是整体元素，overflow hidden 从中间切，下边框不补）——视觉正确的跨页需每页重渲染表格子集，超出测量修复范围 | 宽度计量已有两版漂移族史（待办-0016/0018），再添第三版口径 |

**推荐：方案 A-简。** 理由：测量与渲染同 DOM 是本项目分页架构（usePagination 注释自述"DOM 度量分页"）的既定方向；A-行 的视觉缺陷（边框丢失）说明表格行级断点需要渲染机制升级配合，属另一个任务的事；B 与架构逆行。

**快照牵连（有意行为变更，须同步基线）**：`components/Preview/__tests__/previewStructure.test.tsx` 的 Preview 系快照（:259-303，度量容器含表格）中表格从 `<p class="a4-table"></p>` 变为结构化 `<table class="a4-table-element">`——A4Page 系快照（page 模式表格）不变。测试构造 `makeTable`（previewStructure.test.tsx:66-78）的 `content: ''` 字段不受 0005 影响（受 0032 影响，见 §三）。

## 同构与复用判定

**问①：库中有没有逻辑同构的兄弟？——有（弱同构，建议就地实现、不抽共用层，上报裁定）。**

- "度量容器渲染真实结构测高"的既有先例＝**版记**：`Preview.tsx:99` 度量容器渲染 `<A4FooterNote measurer>`（真实 DOM），usePagination :148-153 度量其高度做末页避让。0005 方案 A 是同一逻辑形状（同一类资源：度量容器中的块；同一动作：渲染真结构测高；同一条链路：预览分页）在表格上的**第二实例**。
- 但抽象时机评估：两处语义不同（版记＝独立定位块经 props boolean 传信号；表格＝内容流块经 renderContentFlow 的 mode 参数传信号）。方案 A 落地后 mode 参数消亡、renderContentFlow 彻底同构——**消灭双形态机制而非再造一个**，此时再抽"度量渲染共用层"反而把两个不同生命周期的机制焊死。故建议：就地实现（方案 A），不抽共用层；若未来出现第三种需度量的独立块（如页眉水印）再议抽象。
- 次级同构：usePagination :181-183 的单行分支（标题等整段作为一行）与"表格＝单个 line"是同构形状——直接复用该分支口径，非新造。
- Record<NodeType,…> 全键表（sentenceSplitter :54-86、renderContentFlow NODE_CLASS_MAP :26-39、fonts nodeFontRole :51 等）中的 TABLE 键为 0029 封闭化的穷尽义务填充，非死代码，不动。
